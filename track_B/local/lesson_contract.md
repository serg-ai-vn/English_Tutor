# Контракт исполнения урока P26

## Источник состояния и начало

Общий источник — https://github.com/serg-ai-vn/English_Tutor, main. Папка track_B/local/db — часть репозитория. Старая папка D:/Projects/English/English_Tutor 2.0 — архивный черновик владельца, не источник текущего курса. Не переносить из неё состояние.

Перед планом получить живой SHA main и читать связанные файлы на одном SHA. Локальный origin/main без fetch не доказывает свежесть. При рабочей копии проверить origin, ветку, незакоммиченные изменения; не делать слепой pull/rebase, reset, clean или force-push. Назвать путь и назначение создаваемой копии. При работе через GitHub connector clone не требуется. Чтение не доказывает возможность записи.

Прочитать progress, текущий день программы, очередь, Pending, analytics_contract и этот контракт. Проверить согласованность последнего закрытия. При незавершённом закрытии сначала восстановить его из первоисточника. Номер следующего обычного урока = days_completed+1; Refresher не увеличивает счётчик. Материал из будущей программы не считается изученным. В speaking/data/pitch требовать только подтверждённо введённое; material_exposure со статусом explained не означает освоение или успешный retrieval. Если prerequisite не найден — использовать знакомый материал, не дописывать историю ради плана.

## Время и объём

План 30 минут, цель 25–30; с elapsed 25 минут не выдавать новые задания, safety cap 35. Число заданий — максимум; раннее закрытие допустимо с причиной. SRS 4–5 минут, один пакет до 5, одна проверка и до одного общего retry до 2 минут за счёт основного блока. Остаток основного блока вычислять из реального времени, а не добавлять 25 минут после затянувшегося SRS.

До каждого нового задания проверить elapsed и примерное время ответа: не выдавать задание, которое заведомо не помещается до 25. При длинном SRS сократить объём главного навыка; если времени нет — feedback и Closure. Указывать короткий бюджет ответа. Во время ожидания ученика обычный ответный чат не гарантирует вмешательство в нужную минуту; не обещать автоматическое прерывание. Без часов показывать ~?/30 и действовать по лимиту шагов.

Фиксировать lesson_started_at при подтверждении плана; для SRS batch_issued_at, answer_received_at, clarification/retry timestamps, если реально доступны. Elapsed, learner-reported active time, измеренный model wait и backend save time — разные величины. Неизвестное null; model_wait_excluded true допустимо только при измерении. Не вычитать придуманные паузы. actual_learning_min — целое число из ответа ученика/проверяемого активного таймера; без него закрытие не готово.

Первая строка каждого учебного сообщения: ⏱ [Блок X/2 | Шаг Y из Z | ~M/30 мин], Refresher X/3. X,Y,Z соответствуют реальному плану. Аналитические JSON-only роли не добавляют индикатор в JSON. stop_new_tasks=true, elapsed>=25 или исчерпанный лимит → только feedback и завершение. Пропущенное summary/ход отмечать closed_early, а не выполненным.

| Навык | Верхняя граница внутри оставшегося общего бюджета |
|---|---|
| Grammar | 2 примера, 3 controlled + 2 своих предложения, одна проверка/retry |
| Speaking | 3 содержательных ответа, перенос работа/жизнь, до 3 коррекций |
| Reading | до 3 предслов; 8–10 предложений, >=70% новых фактов; 2 вопроса; при наличии времени summary 30–45 сек |
| Data speaking | 2 хода: описание/интерпретация и короткий перенос/исправление |
| Patterns/listening | 2 паттерна; аудио 1.5–2 мин с транскриптом на первом проходе, 2 вопроса, 2–3 shadowing; весь блок в остатке 25 мин |
| Pitch/mock | 2 хода pitch или до 3 возражений mock; mock только W6–12 |
| Day 7 | 15 минут лёгкого input + 15 weekly review; весь урок 30 минут |
| Refresher | SRS 5 + grammar 12 (до 4 предложений) + speaking 12 (до 2 ходов) + closure 1; новых карточек нет |

## Полнота аналитики

Ученику до 2–3 коррекций по режиму, в ANALYTICS_PACKET — все обнаружимые случаи. Непройденное сохраняется в error_events с not_yet_covered, без штрафа/drill/автоматического error_log или SRS. Исходные слова неизменяемы; corrections отдельно. Новые аудиторские находки — отдельные уникальные события со ссылкой на исходное, capture_status=post_lesson_audit, feedback_shown=false. Они не меняют историческую оценку. Неизвестная модальность/ASR не превращается в подтверждённое произношение.

session_id — ключ сессии во всех новых связанных записях; lesson_number в старых Refresher-записях исторический. date+session_kind различают Refresher перед 9 и обычный Lesson 9. Не создавать повтор по тому же session_id. Каждый содержательный ответ сохраняется дословно в event даже при errors:[]; speaking/pitch/data также в speaking_recordings. Варианты SRS-ответа оцениваются по цели, не по нецелевой грамматике объяснения.

## Закрытие и доказательство GitHub

Тихий бэкенд действует при штатной работе. Ошибка, конфликт, пропуск записи или необходимое действие владельца сообщаются сразу. Учебная часть завершена и сохранение подтверждено — разные состояния.

1. Подготовить единый комплект: дневной лог, одна session, задачи, ответы/аналитика, результаты только предъявленных SRS, progress, today, session.md, Pending. speaking/error_log/assessments/новые SRS — только если применимо; иначе явно not_applicable с причиной в manifest. Не создавать выдуманные строки ради чекбокса.
2. До записи выполнить node track_B/local/lesson_tools.cjs validate и тесты. Составить manifest с base_main_sha, session_id, reviewed_ids, списком файлов и ожидаемыми хешами. Локальная проверка не подтверждает публикацию.
3. Одним коммитом опубликовать весь комплект на свежем main: локальный Git или Git Data API tree/commit с проверкой исходного SHA. Только явные пути, без слепого git add -A. Другой писатель продвинул main → заново прочитать/согласовать; не force-push. При API по одному файлу использовать временную ветку и слияние полного комплекта. Если это невозможно — оставить переносимый пакет и статус сохранения незавершённым. PR без merge не означает main updated.
4. После таймаута проверить, не применена ли операция, прежде чем повторять. Закрытие идемпотентно: повтор того же session_id не добавляет сессии, ошибки, reps или progress. Ровно один оркестратор пишет.
5. После публикации получить удалённый SHA main; убедиться, что commit входит в его историю; перечитать все файлы комплекта на опубликованном SHA и сравнить хеши/содержимое. При продвинувшемся main проверить, не потеряны ли данные. Только после этого статус verified_main и итог: «Сохранено в GitHub/main: урок N, лог [ссылка], коммит [ссылка], комплект проверен». Квитанция выдаётся после commit; commit не должен содержать собственный будущий SHA.

Если запись не подтверждена, ПЕРВАЯ строка: «Учебная часть завершена. Сохранение в GitHub не завершено: <причина>». Никакого общего Completed сверху. Назвать настоящее местонахождение результатов: переписка, конкретный локальный файл, ветка/PR. Не говорить «локально», если файла нет. Включить доступный точный текст ошибки без секретов. Техническая авторизация терминала и connector может различаться; допустимый канал доступен при техническом отсутствии credentials, но запрет политики нельзя обходить другим каналом. При временной сети до двух повторов, затем понятное действие владельца. Не завершать молча.

## Проверки и границы

node track_B/local/lesson_tools.cjs validate — проверка базы; queue 11 — очередь; node --test track_B/local/lesson_tools.test.cjs — проверки отказов/повторов. Чистые функции prepareClosure и verifyReceipt используются оркестратором до записи/после перечитывания, сами сеть/файлы не меняют. При отсутствии runtime применить тот же чек-лист вручную и указать, что исполняемая проверка не запускалась. Даже успешные тесты не гарантируют соблюдения инструкции любой моделью и не создают фонового таймера.
