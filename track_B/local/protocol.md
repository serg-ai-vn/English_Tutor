# Протокол урока

Это канонический протокол Track A. Любая среда исполнения (**OpenCode**, **OpenAI Codex**, **Claude Code**, **Cursor / Windsurf** или веб-чат) исполняет одну и ту же программу по единым промптам из `track_B/prompts/`. Схема JSON-файлов в `track_B/local/db/` сохраняет совместимость для будущей миграции в Supabase.

## Роли и границы

- **Основной чат — оркестратор и единственный писатель (`Single Writer`).** Он планирует урок, записывает `track_A/today.md`, передаёт узкий контекст в учебные блоки и после урока обновляет JSON-базу, логи и Git-репозиторий.
- **Учебные блоки — read-only роли.** Каждый учебный блок работает строго по своему промпту из `track_B/prompts/*.md` и контракту `track_B/prompts/analytics_contract.md`:
  - В **Codex**: вызываются субагенты `.codex/agents/*.toml` (которые напрямую читают `track_B/prompts/*.md`).
  - В **OpenCode**: вызываются субагенты `.opencode/agents/*.md` (которые напрямую читают `track_B/prompts/*.md`).
  - В **других средах**: вызывается read-only субагент (через `Task` tool) или включается режим строгой ролевой изоляции напрямую по `track_B/prompts/*.md`.
- Одновременно разрешено до 3 субагентов. Обычные блоки идут строго последовательно; три параллельных вызова используются только для расчёта медианы `check_monologue_caf.md` на бенчмарках W4/W8/W12.
- Учебный блок получает буквальное содержимое `track_A/today.md`, `track_B/prompts/analytics_contract.md` и только нужный для его блока payload. Самостоятельно расширять контекст, читать логи, архивы или писать файлы он не имеет права. Learner-facing ответ остаётся компактным; отдельный `ANALYTICS_PACKET` получает только оркестратор.

## Старт нового урока

Команда ученика: **«Начинаем урок»** (или **«У меня был перерыв, давай повторим пройденное»**). Быстрый маршрут описан в `track_A/LESSON_START.md`.

1. При наличии доступа к терминалу/Git оркестратор молча выполняет `git pull --rebase` в ветке `main`.
2. Оркестратор читает `track_A/progress.json` (включая накопительные списки `covered_grammar` и `introduced_material`) и вычисляет `lesson_number = days_completed + 1`.
3. Из `track_A/program/program.json` берёт только текущую неделю и позицию дня, не весь курс (либо включает **Режим повторения после перерыва `Refresher`**, если ученик попросил освежить пройденный материал перед тем, как идти дальше).
4. Из `track_B/local/db/srs_items.json` выбирает только карточки с `status != "deprecated"`, `reps > 0`, `due_lesson <= lesson_number`. Сортировка обязательна и детерминирована: **`(due_lesson ASC, lapses DESC, id ASC)`**. Из отсортированной очереди берутся первые максимум 5 карточек; порядок записей в исходном JSON не имеет значения.
5. Все выбранные `front` выдаются одним нумерованным пакетом (`1–5`). Ученик отвечает на 1–5 одним сообщением (`не помню` — допустимый ответ), затем получает одну общую проверку. Только карточки с ошибкой получают один общий retry; новых примеров и дополнительных раундов нет.
6. Первичный retrieval планируется на 5 минут learner-active time: от момента, когда пакет показан ученику, до получения его ответа. Время генерации пакета, проверки и других model/agent waits не считается. Единый retry может занять максимум ещё 2 learner-active минуты. Всё фактическое SRS-время сверх первых 5 минут сокращает главный блок на ту же величину, поэтому общий урок не удлиняется. Не показанные карточки остаются без изменения.
7. Новые карточки не берутся из общего пула автоматически. Они создаются только из материала главного навыка: максимум 2 за урок. После фактического ввода и подтверждения ученика новая карточка получает `status: "active"`, `reps: 1`, `lapses: 0`, `interval_lessons: 1`, `due_lesson: lesson_number + 1`; `reps: 0` зарезервирован для ещё не введённых seed-элементов. Одна повторяющаяся высокочастотная ошибка может заменить одну из двух, но не добавляется сверх лимита.
8. Оркестратор перезаписывает `track_A/today.md`, показывает один компактный план и ждёт подтверждения.
9. После подтверждения каждый учебный блок передаётся соответствующему агенту вместе с контрактом тихой аналитики (`track_B/prompts/analytics_contract.md`).

Календарь не управляет курсом. Пропуск дня или двухмесячный перерыв не создаёт долг и не увеличивает урок.

## Режим повторения после перерыва (`Refresher Lesson`)

Если у ученика был перерыв в занятиях и он просит **повторить пройденное** перед следующим уроком программы:
- Счётчик `days_completed` в `track_A/progress.json` **не увеличивается** (урок записывается как `Refresher` для восстановления навыка перед `Lesson N`).
- Длительность: 25–30 минут (hard cap 35 минут).
- Структура:
  1. `srs_review` (5–7 мин): пакет из 5 самых старых карточек по `(due_lesson ASC, lapses DESC, id ASC)` + до 1 retry по ошибкам.
  2. `grammar_lesson` + `check_grammar` (15–20 мин): краткая сводка-напоминание всех тем из `covered_grammar` и 6 практических предложений на их различение (без ввода новых времён).
  3. `tutor_speaking` (15–20 мин): живой диалог на 4–5 ходов по ключевым фактам и цифрам из `introduced_material` с отложенной коррекцией (до 3 правок).
- Закрытие: обновляются интервалы показанных 5 карточек в `srs_items.json` (новые карточки не добавляются), создаётся дневной лог `YYYY-MM-DD.md`, добавляется запись в `lesson_sessions.json` (с пометкой `Refresher`) и `error_events.json`, а `days_completed` остаётся прежним, чтобы на следующем занятии штатно запустился `Lesson N`.

## Семидневный учебный цикл

### День 1 — Grammar, 25–30 минут

- `srs_review`: один пакет до 5 карточек, 5 минут learner-active retrieval; только при ошибках один общий retry до 2 минут с компенсацией из времени grammar-блока.
- `grammar_lesson`: один узкий target или контраст, 20–25 минут. Номер юнита в программе — только метка темы; книга ученику не нужна.
- `check_grammar`: 10–15 минут, максимум две приоритетные коррекции и одна повторная попытка.
- До 2 новых SRS-карточек из фактически введённого материала.

### День 2 — Speaking, 25–30 минут

- `srs_review`: один пакет до 5 карточек; 5 минут retrieval + при необходимости один общий retry до 2 минут за счёт speaking-блока.
- `tutor_speaking`: 30–35 минут, максимум 6 содержательных ходов ученика.
- Только `covered_grammar` и `introduced_material`. Новый C1-паттерн не вводится.
- Отложенная обратная связь: максимум 3 коррекции, 2 chunks и одна повторная попытка.

### День 3 — Reading, 25–30 минут

- `srs_review`: один пакет до 5 карточек; 5 минут retrieval + при необходимости один общий retry до 2 минут за счёт reading-блока.
- `reading_tutor`: 30–35 минут.
- До текста: максимум 3 необходимых слова с переводом. Текст: 10–14 предложений, не более 30% известных фактов с пометкой `(review)`. После: 3 вопроса и саммари 60–90 секунд.
- Максимум 2 новых chunks в SRS.

### День 4 — Data speaking, 25–30 минут

- `srs_review`: один пакет до 5 карточек; 5 минут retrieval + при необходимости один общий retry до 2 минут за счёт data-speaking блока.
- `data_speaking`: около 35 минут. Ученик сначала описывает, затем интерпретирует данные.
- Два переноса в рамках одного навыка: профессиональный кейс и более общий рабочий/повседневный кейс.
- Только уже введённый материал; максимум 3 отложенные коррекции и 2 chunks.

### День 5 — Patterns + listening, 25–30 минут

- `srs_review`: один пакет до 5 карточек; 5 минут retrieval + при необходимости один общий retry до 2 минут за счёт основного блока.
- `patterns_listening`: ровно 2 запланированных разговорных паттерна, затем 18–22 минуты listening и 10–12 минут drilling.
- Перед незнакомым акцентом: субтитры/транскрипт на первом проходе и максимум 3–5 предслов до прослушивания.
- Listening нельзя подменять чтением. Если аудио недоступно, блок останавливается и оркестратор предлагает доступный источник, не выдумывая факт прослушивания.
- Два паттерна и есть лимит новых карточек этого урока; дополнительные chunks не создаются.

### День 6 — Pitch, 25–30 минут

- `srs_review`: один пакет до 5 карточек; 5 минут retrieval + при необходимости один общий retry до 2 минут за счёт pitch-блока.
- W1–W5: `pitch_coach`; W6–W12: `mock_pitch` с явно переданными возражениями.
- Практика использует только введённый материал. В practice mode — максимум 3 коррекции и одна повторная попытка.
- Полный рубрикатор и CAF не запускаются после каждой репетиции.

### День 7 — Light review / benchmark, 25–30 минут

- Обычный цикл: лёгкий input или чередующийся 2-минутный audio sample (ESP / general English) без оценки, затем `weekly_review`.
- `weekly_review` анализирует последние 7 завершённых уроков из `lesson_sessions.json`, случаи из `error_events.json`, агрегированный `error_log.json`, фактическое время и SRS. Он выбирает максимум два сигнала и одну замену в следующем цикле; объём не увеличивает.
- W4, W8 и W12 benchmark разделён без перегруза: benchmark-монолог/питч и `check_monologue_caf` ×3 идут в day 6, а EF SET reading+listening — в day 7. Оркестратор считает медиану и не объединяет оба среза в один урок.

## Две шкалы цели

- **12 недель:** функциональный B2+/приближение к C1 в презентации, продаже и профессиональном Q&A. Это не обещание полного C1 за 12 недель.
- **Долгосрочно:** уверенный общий spoken C1 для работы, преподавания, клиентов, партнёров и повседневной жизни.

Баланс тем: около 50% AI-курс/продажи, 30% преподавание/AI-работа/клиенты, 20% повседневная и социальная речь. Перенос делается внутри главного навыка, без дополнительного блока.

## Режим коррекции

- Контролируемая grammar/drill практика: target-ошибка исправляется сразу, затем одна повторная попытка.
- Свободная speaking/pitch практика: не перебивать; в конце максимум 2–3 высокополезные коррекции.
- Ошибка в непройденной структуре помечается `not yet covered — info`, не штрафуется и не попадает в агрегированный `error_log` или SRS; для аналитики occurrence сохраняется в `error_events.json`.
- SRS-карточкой становится не каждая ошибка, а только повторяющаяся или сильно мешающая коммуникации ошибка в уже пройденном материале.
- Ограничение 2–3 коррекции относится к показу ученику. Агент молча возвращает оркестратору все обнаружимые случаи по `analytics_contract.md`; оркестратор сохраняет verbatim wording, coverage и уверенность, не превращая каждую запись в drill.

## Канонический формат `track_A/today.md`

1. YAML frontmatter с номером урока и датой обновления.
2. Цель, главный навык, плановое время и hard cap 35 минут.
3. Таблица: блок, минуты, агент/промпт, ожидаемый результат.
4. `SRS reviews`: точный отсортированный пакет максимум из 5 `id + front`, ключ сортировки `(due_lesson ASC, lapses DESC, id ASC)` и поля времени пакета/retry; новые элементы отдельно и максимум 2.
5. `introduced_material`: весь ранее введённый материал, который разрешено требовать сегодня.
6. `covered_grammar`: структуры, по которым разрешено оценивать.
7. `not_scored_yet`: известные, но ещё не освоенные структуры.
8. Источники и payload для агента; весь учебный материал всё равно выдаётся в чате.
9. Чек-лист закрытия и раздельные поля `planned_learning_min` / `actual_learning_min` / `model_wait_min`.

## CAF — только benchmark

1. `check_monologue` (`check_monologue.md`) получает transcript, `mode: benchmark`, `covered_grammar`, `introduced_material`.
2. Тот же исходный transcript без очистки параллельно получают три экземпляра `check_monologue_caf` (`check_monologue_caf.md`).
3. Оркестратор берёт медиану 7 полей (при необходимости используя `node track_B/local/median.js`): `t_units`, `words`, `errors`, `e_per_100`, `eft_per_t`, `mlt`, `subordination`. Разброс более 15% от медианы помечается `reliable: false`.
4. Результат сохраняется в существующие `speaking_recordings.json`, `assessments.json` и дневной лог без изменения схемы.

## Закрытие урока и синхронизация с GitHub

Оркестратор делает это сразу и молча после последнего блока:

1. До смены статуса урока на `completed` получает `actual_learning_min` (продуктивное время учёбы в целых минутах из явного ответа ученика или проверяемого таймера), отдельно отмечает `model_wait_min` и причину отклонения, затем создаёт дневной лог по `track_A/logs/_template_daily.md`. Значения «не зафиксировано» и оценка «на глаз» недопустимы.
2. Добавляет одну запись урока в `lesson_sessions.json`; `actual_learning_min` никогда не заменяется диапазоном сообщений или общей продолжительностью чата.
3. Обновляет `daily_tasks.json` по фактически выполненным блокам. `duration_min` сохраняется как legacy-поле; новые записи также различают `planned_duration_min` и `actual_duration_min`, если block actual известен.
4. Переносит `ANALYTICS_PACKET` в `error_events.json`; speaking/pitch/data attempts с verbatim transcript — в `speaking_recordings.json`. Ученику полный пакет не показывается.
5. Обновляет интервалы просмотренных SRS (`easy`: `reps + 1`, увеличение `interval_lessons`, `due_lesson = lesson_number + new_interval`; `lapse`: `lapses + 1`, `interval_lessons = 1`, `due_lesson = lesson_number + 1`); непоказанные карточки не меняет. Добавляет максимум 2 новых карточки из фактически введённого материала (`status: "active"`, `reps: 1`, `interval_lessons: 1`, `due_lesson: lesson_number + 1`).
6. В `error_log.json` обновляет только агрегированные recurring/high-impact covered errors; отдельные slips остаются occurrence-событиями в `error_events.json`.
7. Обновляет `track_A/progress.json` (включая пополнение `covered_grammar` и `introduced_material`) и добавляет короткую запись в `session.md`.
8. Если доступен Git, выполняет `git add -A && git commit -m "Lesson N completed" && git push` в основную ветку `main` (либо создаёт/сливает PR в `main`, если облачная среда работает через временные ветки).
9. Ученику сообщает одним коротким итогом результат и тему следующего урока.

## Правила данных

- `program.json` во время урока только читается; содержательные изменения вносятся отдельным согласованным патчем.
- JSON-строки не удаляются: устаревшие элементы получают `status: "deprecated"`, ошибки — `resolved: true`.
- `due_lesson` и `interval_lessons` измеряются уроками, не календарными днями.
- Субагент не пишет в JSON и логи. Один писатель — один источник состояния.
- `lesson_sessions.json` — один объект на урок; `error_events.json` — append-only occurrence log; `error_log.json` — агрегированные педагогические кандидаты, а не полный архив.
- Исходная learner wording сохраняется дословно. Исправленный текст хранится рядом и никогда не заменяет источник.

## P25 — Dual Timebox Guard (обязательный стандарт с 2026-10-27)

- Любой урок, включая Day 7, Refresher и benchmark: **25–30 минут**, план 30 минут, **hard cap 35 минут**. На **25-й минуте новые вопросы и упражнения прекращаются**, следует только короткий feedback (максимум 2–3 коррекции) и Closure. Достигнутый последний шаг блока закрывает блок без дополнительного вопроса.
- Оркестратор при подтверждении плана фиксирует `lesson_started_at` по доступным системным часам (bash `date +%s`, PowerShell `Get-Date` или другой реальный clock/timestamp). Исключать из learner-active time только **измеренные** паузы/ожидание модели; для safety hard cap ориентироваться на доступное elapsed time без выдуманных поправок. Если часов нет — применять фиксированный лимит шагов, не называть оценки `~M` измерением времени; после занятия спросить целое `actual_learning_min` и записать неизвестный `model_wait_min: null`.
- Первая строка **каждого учебного сообщения** оркестратора и субагента: `⏱ [Блок X/2 | Шаг Y из Z | ~M/30 мин]` (X и Z — реальные значения текущего плана; для Refresher допускается `Блок X/3`). При отсутствии часов показывать `~?/30 мин` и честно пояснить: нет доступа к таймеру, действует Step Budget. Таймер не заменять количеством ходов: это **две независимые защиты**.
- Все 12 read-only ролей получают от оркестратора `step_index`, `step_total`, `elapsed_min` (или null), `time_source` и `stop_new_tasks`.
